- [x] 2. Flexible recursive split-layout system, replacing the fixed 1/2/4-layout model above
  - **Confirmed with the user**: "horizontal parallel" = the side-by-side layout that already existed; "vertical parallel" = new, stacked top/bottom. Also confirmed to go beyond a few more named presets — a full VS-Code-style recursive split tree where any pane can be split in either direction on demand, reaching arbitrary arrangements (not just a fixed menu of shapes) — since this also sets up Part 4 topic 3 (auto-split-on-drag-to-edge, still not built) as a natural follow-up.
  - **Key architecture decision**: kept two identity schemes deliberately independent. `S.builder.panes` stays a flat, index-based array — every tab-management function built in Part 3/Part 4 topic 1 (drag-reorder, cross-pane move, pop-out-to-window, close/switch, `paneIdx` baked into dozens of `onclick` template strings) needed **zero changes**. A new, separate `S.builder.layoutTree` describes only the geometry: leaves are `{type:'leaf', paneIndex}` pointing into the flat array, splits are `{type:'split', dir:'h'|'v', ratio, id, a, b}`. Splitting/closing a pane only ever touches this second tree, never the tab-management code.
  - `builderSplitPane`/`builderClosePane` mutate tree nodes **in place** (a leaf becomes a split, or a parent gets overwritten with its surviving sibling's fields) rather than replacing references — so a node's parent never has to be told about a new child object. Closing folds tabs into the sibling's first leaf (same "fold into survivor" convention the old fixed-layout model used) and renumbers every later `paneIndex` after the flat-array splice.
  - **Bug found and fixed during live verification**: `Object.assign` for the in-place node mutation above doesn't clear fields left over from a node's previous `type` (e.g. a promoted leaf keeping its old split's stale `ratio`/`a`/`b`, confirmed via `JSON.stringify` on the live tree mid-test). Harmless in practice — every reader branches on `node.type` first — but a real landmine for future code that doesn't. Fixed with a `mutateNode()` helper that clears all of a node's own keys before reassigning, so a node's shape always matches its current `type` exactly.
  - Rendering (`renderLayoutNode`) recurses the tree, reusing existing `.bpane`/`.bsplit` DOM elements by index/id rather than tearing anything down — relies on `element.appendChild(existingNode)` **moving** an already-attached node rather than destroying it, so a pane surviving a further split or a sibling's closure keeps its live content (mounted editors, listeners) exactly like the old fixed-grid renderer's unfocused-pane guarantee.
  - Resize handles are now per-split-node (`ensureSplitHandle`, one per `.bsplit`) instead of at most one-of-each globally — `startBuilderSplitResize` closes over the specific node reference being dragged, so siblings/other splits are provably unaffected (verified live: resizing an outer split's ratio left an inner nested split's own ratio unchanged).
  - Title-bar `#layout-menu` repurposed from a 3-item `[1,2,4]` list into a one-shot preset gallery (`builderResetToPreset`: `1`/`2h`/`2v`/`3`) — labels stay numeric/symbolic ("1×"/"2×"/"3×", `data-no-i18n`), matching the original menu's own convention exactly, so **no new i18n keys were needed for the menu itself**. Only 2 new keys (`splitPane`/`closePane`) were needed, for the new per-pane split/close button tooltips.
  - **Deliberate behavior change**: split ratios and the tree shape are no longer persisted to `localStorage` across restarts (Part 4 topic 1's `colRatio`/`rowRatio` persistence is removed along with the code that used it) — a ratio has no meaning without the specific tree shape it belonged to, and that shape was never persisted either (tabs/panes are already pure in-session state). Simplification, not a regression.
  - Removed rather than left as dead code: `builderSetLayout`, `builderPaneGridArea`, `applyBuilderGridTemplate`, `ensureBuilderHandles`, `startBuilderColResize`, `startBuilderRowResize`, `BUILDER_COL_RATIO_KEY`, `BUILDER_ROW_RATIO_KEY`, and the `.bl-1`/`.bl-2`/`.bl-4` CSS rules — confirmed via repo-wide grep that nothing else referenced them.

## Part 2 — UI/UX pass: visual system, surgical (2026-07-25)

Files: `style.css` (the bulk), plus a mechanical `--fsc` sweep across 16 renderer files.

Ordering mattered here and was followed strictly: every no-op step landed before the one step that changes pixels, so a regression would stay bisectable.

- [x] 2.1 **Token hygiene.** Declared `--fsc:1` in `:root` — it was referenced 300+ times as `var(--fsc,1)` but never declared anywhere; `core.js` sets it inline on `documentElement`, which still wins, so declaring it is provably a no-op and simply makes the token real to anyone reading `:root`. The 306 `,1` fallbacks were deliberately **not** stripped (300+ edits, zero benefit). Deleted dead `--bg3` (declared on `body`, zero consumers) and amended its comment; kept `--bg2` (3 consumers). Decided **not** to add `--button` to the 19 themes missing it — it is always consumed as `var(--button, var(--accent))`, so adding 19 lines of `--button: <same as accent>` would be pure noise; documented in `:root` instead. `--ui-scale` is likewise unconsumed in CSS but written by `core.js`, so it was kept and annotated rather than removed.
- [x] 2.2 **Missing scales added (declarations only).** `--sp-0..7`, `--fs-micro..xl`, `--lh-*`, `--shadow-pop/float/menu/modal`, `--mono`. Values are the **measured modes of the existing file**, not invented, so new code matches the existing rhythm instead of introducing a second one. The `--fs-*` tokens bake in `calc(Npx * var(--fsc,1))` so new code structurally cannot repeat the bypass fixed in 2.7. The ~2,200 existing px literals were explicitly not retrofitted.
- [x] 2.3 **Shadow retrofit, exact matches only.** 12 `box-shadow` declarations whose values were byte-identical to one of the 4 new tokens, replaced via literal string split/join anchored on the `box-shadow:` prefix so the `:root` declarations themselves could not be rewritten. The 4 near-miss values (e.g. `0 24px 60px rgba(0,0,0,.5)`) were left alone — folding those into a token *is* a look change, however small, which the surgical constraint excludes.
- [x] 2.4a **`--on-accent`/`--on-button`/`--on-danger`/`--ink-dark` introduced; 28 `#fff` swapped.** `#fff` was hardcoded as "ink on a filled surface" across a stylesheet where 32 themes set `--accent` freely. Each `#fff` was classified by reading what its rule's fill actually is, not by pattern-matching: 20 on `var(--accent)`, 2 on `var(--button, var(--accent))`, 4 on `var(--danger)`, and **2 genuine bugs** where the fill is `var(--hover)` and white text was invisible on all 8 light themes (`.dark-table tbody tr.active td` → `var(--t1)`, `.btn-g:hover .icon-danger` → `var(--danger)`). 9 were left as literal white on purpose — they paint against *user-chosen* colors or arbitrary hues (`.graph-label`, `.rel-node`, `.map-point`, the color wheel, `.chr-cal-ev`). Applied by a line-targeted script that asserts each line still contains `#fff` before rewriting and that none remains after, so a shifted line fails loudly instead of being silently rewritten. All three tokens default to `#fff`, making this step computed-value-identical in every theme. **They are three independent literals on purpose** — `--on-button:var(--on-accent)` would hit the exact aliasing trap the existing `--bg2` comment documents, where a per-theme override never reaches the alias.
- [x] 2.4b **Per-theme overrides — the one step that changes pixels.** Contrast was recomputed independently (WCAG relative luminance, white vs each theme's `--accent` and its effective button fill) rather than trusting the planning numbers; the result matched exactly. Overrode to `--ink-dark` in **15 themes for `--on-accent`** and **12 for `--on-button`**, threshold 3:1. Verified before applying that **no flip makes contrast worse**. **Two tokens are genuinely required, not one**: `blueEclipse` has `--accent:#191970` (14.85 against white — white is correct) but `--button:#c9ccd4` (1.61 — white unreadable), so a single token could not express it. Its pre-existing one-off patch (`.btn-p,.modal-actions button{color:#1a1a26}`) was removed, since it was correcting the `--button` fill via per-component selectors and would otherwise have double-applied and outlived the `.modal-actions` deletion in 2.6. **Deliberately not done**: `--on-accentH`. 25 of 32 themes fail 3:1 against the lighter `--accentH` hover fill, but fixing it means either flipping `.btn-p` ink in 25 themes or making the label color flicker on mouseover — the real defect is that `--accentH` is a *lighter* hover on a filled button, which is a restyle, not a defect fix.
- [x] 2.5 **Thai typography.** Thai is the app's default UI language but no Thai-capable face was named in the stack. Inserted `'Leelawadee UI', Tahoma` **after** `'Segoe UI'` — which covers Latin/Greek/Cyrillic completely, so the additions are only ever reached for codepoints it lacks and **no Latin glyph changes**; the emoji/symbol faces stay in positions 1–2 because emoji are used as icons throughout. Both ship with Windows and the build targets are win/nsis only, so no webfont or vendored file is involved. Replaced `word-break:break-word` with `overflow-wrap:break-word` at 4 long-text surfaces: the former is spec-defined as `overflow-wrap:anywhere`, which suppresses Blink's ICU dictionary Thai segmenter and breaks mid-syllable (Thai has no inter-word spaces); the latter still contains long unbreakable URLs, the original intent. **Line-height was measured, not bumped**: `th` is the default locale, so a global `html[lang="th"]` bump would reflow the app's default appearance. All 13 `line-height:1` sites were inspected and every one renders only emoji, symbols or numerals — the three flagged during planning as "can hold translated Thai" turned out to be the ✕/+/x glyph buttons. Correct outcome was therefore **zero line-height edits**.
- [x] 2.6 **Dead CSS removed.** 12 compat-layer classes with **zero** consumers anywhere in `src/` or `index.html` (verified by raw substring grep, which also catches `classList.add`/`className`/template-literal usage, not just `class="..."`): `.panel-item`, `.ph-add`, `.detail-header`, `.detail-actions`, `.section-head`, `.desc-card/-title/-content/-actions`, `.tag-picker`, `.btn-xs`, `.modal-actions`. Plus a block that re-defined `.empty h3/p`, `.tag`, `#toast` and the 4 scrollbar rules verbatim a few lines below their originals. **`.btn-xs` could not be deleted line-wise** — it shared two `.danger` selector lists with `.btn-sm` (20 consumers), so those selectors were trimmed first. Classes that *look* similar but are live were confirmed kept (`.btn-sm` 20, `.form-row` 17, `.detail-head` 7, `.tag-chip`, `.tab-btn`, `.pick-list/-item`, `.btn-danger`, `.link-chip`). The planning note claiming `.note-section`/`.detail-tags` were duplicated was a **false positive** — those are complementary box vs. flex-`order` rules, deliberately split — and were left untouched. Brace balance re-checked (1337/1337) after the deletions.
- [x] 2.7 **`--fsc` bypass sweep.** 126 inline `font-size:Npx` across 16 renderer files did not scale with the font-size accessibility setting (which clamps to 80–130%). Rewritten to `font-size:calc(Npx * var(--fsc,1))`, which at 100% computes to exactly the original px — so the diff is a provable no-op at default settings. A class-per-size approach was rejected (≈15 new utility classes *and* still editing all 126 sites, each a checker-warning risk); a JS helper was rejected because the sizes sit inside mixed declaration strings. Confirmed safe before running: SVG uses the unitless presentation-attribute form, which a `px`-anchored regex cannot match; there are no `ctx.font` canvas assignments; the 27 `em`/`rem`/`%` values already scale via `body{font-size:calc(14px*var(--fsc,1))}`. Piloted on `director.js` (10 sites) before the rollout, and every renderer file `node --check`ed afterward.
- **Verified live via `run-dracondex`, real Electron, this session.** The strongest evidence is a **measured** one rather than a visual one: a probe injected `.btn.btn-p` and `.nav-btn.active` elements, switched through all 32 themes, and computed the real WCAG contrast from `getComputedStyle`. Result: **zero failing themes**; worst button contrast 1.61 → **3.19**, worst nav 1.67 → **3.53**; and the untouched themes still measured exactly their pre-change values (daylight 5.17, midnight 4.47, redEclipse 3.87), confirming 2.4a was value-identical for them. **A measurement bug was caught and fixed mid-verification**: the first probe reported an identical 5.17 for every theme, because Chromium caches computed style per element within one synchronous task, so reusing a single probe across theme switches reports the *first* theme's colors throughout — fixed with fresh elements plus a forced layout read per iteration. Also screenshotted `clearMeteor` (amber accent, now dark ink), `clearSky`, and `blueEclipse` (which correctly shows dark ink on its light button while keeping white on its dark-navy nav — the split case). Font scale checked at 80/100/130%: a swept inline `font-size` measured 12px at 100% and **15.6px at 130%**, confirming the bypass is gone; no clipping or overflow at 130%, Thai tone marks intact. `.dv` confirmed as `overflow-wrap: break-word` / `word-break: normal` with `Leelawadee UI` present in the resolved font stack.
- `check.mjs` held at **0 errors / 31 warnings** after every step, and a final `--fresh` end-to-end run (create vault from the welcome modal) completed clean.

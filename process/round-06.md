### Part 1 — Builder + Hub fixes
- [x] Builder — auto-close a pop-out window once its last tab closes
  - `builderCloseTab` (`builder.js`) now checks `S.isPopup && builderState().panes.every(p => p.tabs.length === 0)` right after the pane-empties branch and calls `api.window.close()` — a popup always starts as a single leaf pane with no parent split node, so the existing `builderCloseIfEmpty` fold-into-sibling path is always a no-op for it and previously left an empty popup window behind.
- [x] Builder — tab-bar slider reorder landed tabs in the wrong slot
  - Root cause: `onTabDrop`'s same-pane reorder re-derived a target key + before/after zone from the dragged tab's **live** bounding rect at drop time, which could already be transform-shifted by the drag-over reflow animation and disagree with what the animation had visually shown. Fixed with `builderMoveTabToIndex` — same-pane drops now insert at the exact index (`drag.curIndex`) the reflow animation was already driving, computed once from the frozen pre-drag rects, instead of re-deriving it from a possibly-stale live rect.
- [x] Builder — tabs shouldn't overflow into a horizontal scrollbar; shrink to fit, down to icon-only
  - `.bpane-tabs .project-tab` changed from `flex-shrink:0` to `flex:1 1 0;min-width:28px;max-width:200px` (`style.css`) so tabs shrink together to fill the bar. A new `syncTabBarCompact(barEl)` (`builder.js`) measures `clientWidth / tab-count` against a `TAB_COMPACT_THRESHOLD` of 90px and toggles a `.tabs-compact` class that hides `.tab-name`/`.ek`/`.tab-dot` and shows a new `.tab-kicon` (module/kind icon) instead — resynced from three places: every `renderBuilderPanes` pass, a `ResizeObserver` on each pane's `.bpane-head` (survives re-renders since only its `innerHTML` is replaced, not the node itself), and the split-resize `mousemove` handler (since dragging a split handle changes pane width without going through `renderBuilderPanes` at all).
- [x] Hub — icon/symbol collection popup: dock as a fixed-height (4-row), independently-scrolling container
  - Reverses an earlier round's "whole popup scrolls as one block" decision (`.icon-edit-popup{max-height:min(72vh,520px);overflow-y:auto}`) — now only the swatch grids scroll: `#ipk-icon-grid,#ipk-symbol-grid{max-height:162px;overflow-y:auto}` (4 rows × 36px cells + 3× 6px gaps = 162px), while `.icon-edit-popup` itself keeps only a generous last-resort `calc(100vh - 40px)` cap that should essentially never engage. `#ipk-upload-pane` (the crop-import UI, which reuses `.ipk-grid`'s id-selector for an unrelated flex-column layout) is deliberately excluded from the 162px cap — its 220×220px crop canvas would clip badly inside it.
- [x] Hub — creating a module while right-clicked on another module should auto-parent as its child
  - `buildModuleContextMenuHtml`'s "Create" submenu used to always call `openCreateSubmenu(event, null)` regardless of which module's menu was open, so every context-menu creation landed as a new top-level sibling. Now passes the right-clicked module's own `id`, so submenu creations correctly nest as its child.
- [x] Hub — add a "create Collection" button on the Nest header, next to "create Major module"
  - Nest section's header (`buildHubHtml`) now renders `quickCreateModule('collector',null)` (one-click, auto-named + inline-rename, reusing the collector kind icon as the button glyph) immediately before the existing `openMajorModuleModal` "+" button.
- [x] Hub — move "Collection" out of the create-kind submenu, onto the context menu directly as its own "Folder create" row
  - `buildKindListHtml` gained an `excludeCollector` flag, passed `true` only from the context menu's hover submenu (`openCreateSubmenu`) — every other "+" popup (Nest header, Minor-module create) still lists all 15 kinds including Collector. The context menu itself grew a dedicated Collector row directly below "Add Minor Module", using the kind's own icon/color/description, auto-parented to the right-clicked module exactly like the fix above.
- [x] Hub — dragging a module below an already-expanded parent with children should nest it as a child, not reorder it as a following sibling
  - `nestDropZone(ev, row, id)` gained the `id` parameter: for the bottom-quarter drop band, it now looks up the target node and returns `'in'` (child) instead of `'after'` (sibling) specifically when that node has children **and** is currently expanded (not collapsed) — a collapsed parent, or one with no children at all, keeps the original sibling-reorder behavior. `onNestDragOver`/`onNestDrop` updated to pass the id through.

### Part 4 — Nexus Nest: new "minor module" content-item concept
A genuinely new concept, distinct from the pre-existing "Add Minor Module" feature (a full child `module`-table row) — here "minor module" means one individual **content item** living inside a module's own data (one Classifier object, one Chronicler timeline event, one Author chapter, one ChatScribe session, one Designer node), previously only a row in a content table with no presence in the Nest tree and no way to open it as its own thing. Scope confirmed with the user across two rounds of questions: applies to the 5 content-bearing kinds with a clean existing single-item field-editor to reuse (Classifier, Chronicler, Author, Scribe/ChatScribe, Designer) — Sketcher/Narrator/Locator deferred (tightly coupled to a live interactive canvas/board with no clean single-item reuse candidate); Collector/Manager/Inspector/Drafter/Viewer have no content-item concept at all; Connector/Wanderer only reference other modules' items rather than owning original content. Item rows load lazily (only on first expand of their owning module), and the expand chevron is gated by a real item **count**, not shown unconditionally.

- [x] 1. Show content items as their own rows in the Nest tree, nested under their owning module
  - New lightweight `getContentItemCounts(nexusRef)` (`src/db/module.js`) — 5 `COUNT(*)` queries (one per in-scope kind, Chronicler's joined through `timeline.module_ref` since events are two levels down) merged into one `{moduleId: count}` map, wired as `module:getItemCounts` (`main.js`/`preload.js`). `reloadModuleTree` (`hub.js`) fetches it in parallel with the existing tree fetch into `S.moduleItemCounts`.
  - New `ITEM_KIND` registry (`src/renderer/mod/item.js`, new file, added to `index.html`'s eager `<script>` list since the Nest tree needs it on every render) — one entry per in-scope kind with `list(moduleId)`, `nameOf()`, and an async `renderBody()`; `list()` is the single fetch primitive reused by the Nest tree's lazy expand, the item's own page, and a shared `fetchOneItem` helper (generalizing the "fetch parent-scoped list, find by id" convention `openChroniclerEventModal` already used, rather than hand-copying it 5 times).
  - `buildNestRow` (`hub.js`) triggers `ensureNestItemsLoaded(m.id)` opportunistically at render time whenever a content-bearing-kind module renders expanded (not only from an explicit expand-click) — necessary because modules start expanded by default, so a click-only trigger would never fire for an already-open Nexus. Chevron visibility (`showChev`) is gated on `hasChildren || (isContentKind && itemCount > 0)`, preferring the live loaded array's length over the pre-fetched count once available. A brand-new `buildNestItemRow` render function (not a `buildNestRow` recursion) renders each item leaf with no `draggable`/drag-event attributes at all, no chevron, no context menu — structurally guaranteeing a content item can never be dragged out of its owning module or be mistaken for a real `module`-table row by `findModuleNode`/`isSelfOrDescendant`/`onNestDrop`.
  - `invalidateNestItems(moduleId, delta)` is called from every content-item create/rename/delete path across all 5 kind files, keeping the chevron count accurate immediately (±1) without waiting for a refetch.
- [x] 2. Give each content item its own dedicated Builder page, showing the same live data as the module's own inline view, still editable from both places
  - New Builder page-ref shape `{kind:'item', itemKind, moduleId, id}`, threaded through `builderPageKey`/`builderParseKey`/`builderOpenPage`/`builderTabMeta`/`builderStaticPageHtml` (`builder.js`) alongside the existing `module`/`file`/`sagehut` refs. New `S.activeItemNode` mutual-exclusion state, added to the same null-out set `openModuleNode`/`openImportFile`/`openSageTab`/`goToNexusNestHub` already maintain for each other.
  - Each kind's item page reuses its module view's existing field editor rather than a parallel rendering path: Chronicler's `buildChroniclerEventInspectorHtml` as-is; Author's `createMarkdownEditor` mounted into a second, distinct container id so both a module's and an item's editor can coexist in split panes; Classifier's `renderClassifierObjectDetail` extracted to accept `templates` as a parameter instead of reading `S.classifierData` ambiently; ChatScribe's thread rendering extracted into `buildChatBubblesHtml(session, messages, opts)` plus new `chatScribeActiveSessionId()`/context-aware send/edit handlers; Designer's node fields extracted into `buildDesignNodeFieldsHtml(n, opts)` with a configurable DOM-id `prefix` so the item page's fields don't collide with the module view's or the modal's.
  - **Bug found and fixed during live verification**: deleting a content item from the module's own inline view updated the Nest tree/chevron immediately (via `invalidateNestItems`), but a *background* (unfocused) Builder tab already open for that same item was never closed — it just sat there showing stale data, since `openItemNode`'s own "item no longer exists, close this tab" check only ever ran if the user re-focused that exact tab. Fixed by extending `invalidateNestItems` to call a new `closeStaleItemTabs(moduleId, wasLoaded)` on any delete (`delta < 0`): it re-fetches the fresh item list, scans every pane's tabs for `item:<kind>:<moduleId>:` keys whose id is no longer present, and closes each via the existing `builderCloseTab` (reusing its active-tab-reassignment logic) with a shared `itemNotFound` toast — no new i18n key needed.
  - Live-verified via `run-dracondex` against real Electron, for all 5 kinds: created/edited test data for each kind; confirmed the Nest tree shows each kind's item leaves correctly nested, lazily fetched (`S.nestItems` populated only after expand), and never draggable; confirmed each item opens its own Builder tab with the correct badge/icon/tab title; confirmed an edit made from the item's own page (Chronicler event story field, Classifier attribute cell, Author chapter markdown, ChatScribe message send, Designer node text) is visible from the owning module's own inline view afterward, and vice versa where applicable — each confirmed against the live DB via direct IPC calls, not just visually. Confirmed the delete-while-a-background-tab-is-open fix directly: opened an item's tab, switched focus to the module's own view, deleted the item from there, and confirmed the background tab auto-closed with the toast and the tree row disappeared with the chevron collapsing correctly.
  - One pre-existing, unrelated timing gotcha surfaced during verification and is worth flagging for future live-testing sessions, not a bug in this feature: after calling a v3 module's own `open*` function via direct `eval` (bypassing a real click), that module's own async data-load (`S.chroniclerData` etc.) needs on the order of 700-900ms to actually populate before calling functions that read it (`selectChroniclerTimeline`, etc.) — a 400ms wait was consistently too short and produced misleading `null`-state failures that looked like app bugs but were purely test-harness timing.

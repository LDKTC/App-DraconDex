## Round 6 — Builder pane/tab bugs (Part 1 only) (2026-07-18)

A fresh `Plan.md` the user wrote after Round 5 closed out, with 4 parts. Per the user's instruction this round tackles **Part 1 only** (5 items, all in the Builder's split-pane/tab-drag system) — Parts 2–4 (nav sidebar rework, tab-bar split-button relocation, chronicler module, dropdown theming) are separate, later rounds. All work is in `src/renderer/builder.js`, plus small touches to `main.js`, `preload.js`, `style.css`, `src/renderer/core.js`, `src/renderer/i18n.js`.

Files: `src/renderer/builder.js`, `src/renderer/core.js`, `src/renderer/i18n.js`, `main.js`, `preload.js`, `style.css`

- [x] 1. Auto-close a pane once it has zero tabs
  - Root cause: `builderMoveTabTo` and `builderCloseTab` both spliced a pane's `tabs` array but never checked whether it went to zero length. New `builderCloseIfEmpty(paneIdx)` helper delegates to the existing `builderClosePane` (reuses its fold-into-sibling + tree-renumber + `b.focused` fixup logic rather than duplicating any of it) — called from both the drag-move path (`builderMoveTabTo`'s cross-pane branch, after the active-tab fixup) and the explicit ×-button path (`builderCloseTab`, checked before the existing active-tab-reassignment branch since that branch used to return early). `builderMoveTabTo` also had to correct its own `paneIdx` parameter when the just-closed source pane's removal renumbers the destination pane's index.
- [x] 1.1. Fixed the bug where a tab reassigned into a sibling pane (via explicit "close pane") spawned a new pop-out window instead of opening in place
  - **Investigated directly rather than guessing**: neither `builderSwitchTab` nor `builderOpenPage` ever touch `api.window.*` — clicking a tab cannot literally create a `BrowserWindow` through that path. The only place that happens is `onTabDragEnd` → `builderPopOutTab`, which used to fire on ANY unaccepted drop end (a known, already-documented HTML5 DnD ambiguity — can't tell "dropped outside the app" from "Escape mid-drag"). Diagnosis: closing a pane collapses the layout and reflows the sibling's tabs to new screen positions right where the user's mouse already is from clicking "close pane" — a fast follow-up click can get misread as a near-zero-movement accidental drag.
  - **Chose the second of the two candidate fixes the user offered**: kept "fold tabs into sibling on pane-close" as-is (already correct/expected), and fixed the actual bug — gated `onTabDragEnd`'s pop-out behind a real "dragged meaningfully far outside its own tab bar AND held it there" signal (`S.dragTab.armed`, `DRAG_DETACH_PX=48` / `DRAG_DETACH_MS=160`, tracked by a new `trackDragArm` function) instead of firing on any unaccepted drop. A reflow-induced micro-drag now correctly no-ops; a genuine drag to the nav-sidebar/title-bar or a genuine Escape-after-real-movement still pop out as before.
  - **Real bug found and fixed during live verification** (not present in the initial write, caught only by driving real mouse drags): `onTabDragOver` calls `ev.stopPropagation()` for every tab hovered — including tabs in a *different*, destination pane. Since `trackDragArm` was originally bound as a normal (bubble-phase) `document` listener, that `stopPropagation()` silently prevented it from ever seeing dragover events once the cursor was hovering an existing tab in another pane — meaning a drag could never arm if it ended up over a populated pane's tab (only empty-strip destinations worked). Fixed by binding `trackDragArm` on the capture phase (`document.addEventListener('dragover', trackDragArm, true)`), which fires before any bubble-phase `stopPropagation()` can block it.
- [x] 2. Add support for dragging a tab from a pop-out window back to the main window
- [x] 2.1. Auto-close the pop-out window once it has no tabs left after such a move
  - **Researched before building** (WebSearch + a tutorial specifically about this exact problem): plain HTML5 `draggable=true` drag-and-drop does not fire natively across separate Electron `BrowserWindow`s — each is an isolated renderer process, confirmed by the standard fix being IPC-based coordination, not native cross-window DnD. Live-testing this empirically wasn't feasible either (Playwright's per-page `mouse.*` API has no way to express "drag from window B's coordinate space into window A's," since each is a separate CDP target with its own viewport-relative coordinates) — went straight to the documented fallback instead of burning a spike on a mechanism known not to work.
  - Shipped as a **click action**, not a drag: a small icon (reusing the existing `I.return` glyph, styled with the same `.tab-close` CSS class as the × button for visual consistency) appears on every tab **only in a popup window** (`S.isPopup`, set early in `core.js`'s `init()` — moved earlier than before so the very first render already knows). Clicking it: closes the tab locally first (`builderCloseTab`, which — thanks to item 1's fix — auto-closes the pane if it empties), tells the main window to open the same tab via a new `window:moveTabToMain` IPC round-trip, then closes the whole popup once **every** pane in it is empty (checked across all panes, not just one, since `.popup-mode` doesn't hide the per-pane split buttons — a popup can be split into multiple panes).
  - New plumbing: `main.js` tracks popup window ids in a `Set` (`popupWindowIds`, added/removed in `createWindow`/`win.on('closed', ...)`) so `window:moveTabToMain` can find "a window that isn't a popup" without needing a full parent/opener registry; `window:getId` (direct `ipcMain.handle`, bypassing the `h()` wrapper since it needs the raw event to resolve `BrowserWindow.fromWebContents`) lets each renderer learn its own window id at boot. No pane/tab *state* crosses the IPC boundary — only `{nexusId, tabKey}`, since tab display metadata (`builderTabMeta`) is derived on-demand from whichever window's own already-loaded data.
  - New i18n keys (all 18 locales incl. `qd`): `moveToMainWindow` (button tooltip), `tabMoveWrongVault` (toast guard in the main window's `onTabInbound` listener, in case the two windows have since switched to different vaults — defensive, since nothing prevents that over a session).
- [x] 3. Tab bar: lock tabs to the bar with live Chrome-style reflow while dragging, detach only past a distance+hold threshold
  - **Transport decision**: kept native HTML5 DnD (not a custom `mousedown`/`mousemove`/`mouseup` pointer-tracker like the split-resize-handle precedent) — a custom pointer-tracker is confined to one renderer's DOM and can't support the OS-level drag session item 4 area needs conceptually, and item 1.1's `armed` flag (a field on the same `S.dragTab`) is directly reusable as the detach gate here.
  - `onTabDragStart` now caches the origin bar's tab geometry (`rects`, `fromIndex`) once at drag start; `onTabDragOver`, for same-pane hover, computes the target slot from cumulative rect midpoints and pushes every OTHER tab aside via `translateX` (CSS `.bpane-tabs.reordering .project-tab{transition:transform .12s ease,opacity .12s ease}`) — replacing the old static `.tab-drop-before`/`.tab-drop-after` box-shadow indicator for the same-pane case (that indicator is kept for the cross-pane hover case, where there's no local reflow to compute). `data-tab-key` added to each tab's markup so drag handlers can identify tabs without re-parsing inline attribute strings.
  - The `armed` gate from item 1.1 is reused, generalized to also gate cross-pane tab-bar drop (`onTabDrop`/`onTabStripDrop`) and drag-to-edge auto-split (`onBodyDragOver`/`onBodyDrop`): an unarmed drop on any target other than the origin bar itself is a no-op (bounces back), matching Chrome's own tab-strip feel. Same-pane reorder is never gated — always instant.
  - Deliberately not changed: `hub.js`'s Nest tree drag keeps its existing static-indicator behavior — different widget shape (nesting tree vs. flat strip), no reason to unify.
- **Test-harness note, not a product bug**: several real-mouse verification attempts initially failed for reasons traced to the test harness, not the app — worth recording since they'd otherwise look like regressions on a future re-run. (1) The first-run welcome modal (opened at boot since the fresh test vault started with 0 nexuses) sat open as a full-viewport `position:fixed` overlay for the whole session unless explicitly dismissed via `closeModal()` — real users never hit this since by the time they have 4+ modules the modal's long gone, but an automated script creating a nexus mid-session doesn't retroactively close it. (2) Chromium's synthetic (CDP-driven) `dragover` firing during a stationary "hold" doesn't repeat on a timer the way it does for a real physical mouse — a hold needed small 1px jitters every ~30ms to keep dragover events (and therefore the `armed` timer) alive. (3) Dragging the *same* element twice in immediate succession was occasionally flaky (drag silently failing to register at all) — switching to a different tab for a second attempt reliably fixed it; likely a CDP/Chromium drag-session settle-time quirk, not reproducible with a real mouse.
- Live-verified via a one-off Playwright script driving real Electron (`run-dracondex`'s Electron binary was available in this sandbox, no 403): real mouse-driven cross-pane drags (with a deliberately-held path to satisfy the new arm threshold) confirmed the auto-close-empty-pane fold-back collapses a split back to one pane; the capture-phase fix confirmed via a drag that lands on an existing tab in the destination pane (previously silently never armed); the `armed` gate directly exercised both ways (`armed:false` → no pop-out, `armed:true` → new `BrowserWindow`, confirmed via `app.windows()` count); same-pane reorder confirmed instant regardless of hold duration; cross-pane drop confirmed to bounce back when released quickly and to succeed when held past the threshold; the move-to-main-window button confirmed end-to-end (popup shows the button, clicking it moves the tab into the main window's focused pane, and the popup auto-closes once empty).
- Ran `node .claude/skills/dracondex-module-style/check.mjs src/renderer/builder.js` (and `core.js`) after every change — 0 errors, no new warnings (the one pre-existing `module-tab` class warning predates this round).

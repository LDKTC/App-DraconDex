## Part 1 — Nexus Nest hover/rename/guide-line polish (hub)

Landed as a mid-plan checkpoint, commit `5873b8a` (v.3.11.1), via `version-update`'s Flow B since Part 2 was still open at the time this part finished. Four small, independently-verified fixes to the Nest tree's day-to-day feel.

- [x] 1. Nest-tree row hover no longer resizes the row. Root cause: `.li:hover .acts{display:flex}` (style.css) revealed two `.btn-i` action buttons sized 28px — taller than the row's own ~22px resting height (13.5px text + 2px×2 padding) — so `.li`'s `align-items:center` flex layout stretched the whole row taller the instant `.acts` appeared. Fixed by adding `.li .acts .btn-i{width:18px;height:18px}` (+ a matching 12px icon size) so revealing the buttons no longer changes row height. Verified with a real before/after screenshot pair via `run-dracondex`'s `web-driver.mjs` (git-stashed the CSS fix temporarily to capture the "before" state).
- [x] 2. Rename mode on a freshly-created module now focuses and fully selects the guideword name immediately, so typing replaces it right away. `startRenameModule()` (`src/renderer/hub.js`) already did this for the dblclick-to-rename path; `quickCreateModule()` (same file), which auto-enters rename mode right after creating a module, never called `.focus()/.select()`. Extracted the shared logic into a new `focusRenameInput(id)` helper, called from both. Verified live: `selectionStart`/`selectionEnd` on the rendered `<input>` matched the full guideword length immediately after creation, and typing over the selection + Enter saved the typed name correctly.
- [x] 3. Click-outside-to-save during rename mode — investigated and found **already correctly implemented** (existing `onblur` handler on the rename `<input>` + `body.renaming-lock` CSS lock from an earlier Part 1 round forcing any outside click to fall through to `<body>` and blur the input). No code change needed; verified live by typing a name, clicking elsewhere, and confirming the typed name persisted and rename mode exited.
- [x] 4. Nest-tree per-depth guide line no longer sits flush against the icon/chevron. The line's `background-position` had been moved (an earlier commit, `6e82a63`) to exactly match `.li.indentN`'s own `padding-left`, leaving a 0px gap that read as touching. Backed all five `.li.indentN::after` rules off by 6px (20/36/52/68/84 instead of 26/42/58/74/90) for a small visible gap — confirmed numerically against live `getBoundingClientRect()` measurements of the guide line vs. each row's own chevron/icon position (a consistent 6px gap at every depth, both chevron-bearing and leaf rows).
- Also patched two pre-existing gaps in the `run-dracondex` skill's `web-driver.mjs` test harness that blocked booting the real app at all in this sandbox (Electron binary download is 403'd here): stubbed `BrowserWindow.fromWebContents` and `ipcRenderer.on` (both were previously unstubbed and threw during renderer boot), and added a `hover` driver command (Playwright's `page.hover`) since none of the existing verbs could trigger a real `:hover` state.

**Part 1 complete** — all 4 items live-verified via `run-dracondex`'s `web-driver.mjs`.

## Part 2 — Import DB hub + Import file (cross-version DB import)

The user keeps older DraconDex versions as GitHub branches (`v.2.1.1-dracondex`, `v.2.7.3-dracondex`) and had already added two even-older sample `.db` files to `old_db_data/` (`novel-manager 1.1.0.db`, `dracondex 1.2.2.db`). They wanted the current app to import a database from any of those older versions or lower, then choose whether to open it read-only in the **Import DB** hub or merge/convert it into the live **Nexus Nest** tree — a choice flow already built in v3.11.0 (`openImportChoiceModal()`/`chooseImportAsNexusNest()`/`chooseImportAsDb()`, `src/renderer/hub.js`). Research (fetching `src/db/*.js` from both branches, and live schema-diffing the two real sample files with Python's stdlib `sqlite3`) found the whole pipeline was already built and only needed a handful of concrete bug fixes to actually work end-to-end for genuinely old files — no new architecture.

- [x] **Import db hub #1** (nav-rail icon bug): `openImportDbHub()` (`src/renderer/core.js`) called `selectModule('director')` but never cleared `S.activeModuleNode` or called `renderModuleRail()` — whatever v3 module/pinned icon was active before stayed marked `.active` in the nav rail even after switching into the read-only legacy Director view. Fixed by clearing `S.activeModuleNode` and calling `renderModuleRail()` on entry, matching the same pattern already used by `selectNexus`/`closeNexus`. Verified live: pinned+opened a v3 module first (confirmed its rail icon showed `.active`), then called `openImportDbHub()` and confirmed via screenshot the stale active-highlight was gone and `S.activeModuleNode` was `null`.
- [x] **Import db hub #2** (view-only enforcement): the read-only guard lives in `preload.js`'s `inv()` wrapper (`IMPORT_DB_READONLY_NS`, a namespace allowlist that rejects any non-`get*` call while `S.importDbMode` is on). Audited it against every `api.<ns>.<fn>()` call reachable from `director.js`/`navigator.js`/`hero.js`/`writer.js` plus `modals.js` (their shared create/edit modals) — found `folder` (project-folder CRUD: `folder.create/update/delete`, used by Director's folder sidebar) was missing from the set, so folders could still be created/renamed/deleted while "read-only" mode was active. Added `folder` to `IMPORT_DB_READONLY_NS`. Also audited `api.wiki.renameTarget` (a mutation reachable from `modals.js`'s `saveObject()`) — left `wiki` deliberately out of the readonly set since it's only ever called *after* the same save's own `api.object.update()` call, which is already gated and rejects first (never actually reached), and most of `wiki`'s own functions are reads that don't start with `get` (`entityPath`/`quickIndex`/`backlinks`/etc.) — blindly gating the whole namespace would have broken those elsewhere in the app. Verified live in one session: `folder.create`/`project.create` both correctly rejected with "Import DB is read-only" while `S.importDbMode` was on, reads (`folder.getAll`, `project.getAll`) still worked, and a separate fresh session confirmed `folder.create` still works normally outside Import DB mode.
- [x] **Import file #1** (sample db files not importable): found and fixed two independent bugs blocking the real sample files, verified against them directly (not just theoretically):
  - **Blocking bug**: both sample files are saved in WAL journal mode with no accompanying `-wal`/`-shm` sidecar — reproduced directly that `node-sqlite3-wasm` aborts hard opening this exact shape (the same method `importDatabaseMerge` used, `src/db/core.js`). `getDB()` already had a working fix for its own db file (patch header bytes 18-19 from `2,2` to `1,1` when no `-wal` sidecar exists); extracted that into a shared `forceLegacyJournalMode(filePath)` helper. `importDatabaseMerge` now copies the picked file to a temp path first (never mutates the user's original file), copies along any real `-wal`/`-shm` sidecars if present, otherwise patches the temp copy's header, opens the copy read-only, and cleans up the temp files in a `finally` block (including `source.close()`) regardless of success or failure.
  - **Secondary bug**: `relation_type` merge block unconditionally selected a `color` column (`SELECT relation_name, color FROM relation_type`) — the older sample file (`novel-manager 1.1.0.db`) doesn't have that column at all (confirmed by diffing the two sample files' full `CREATE TABLE` DDL column-by-column: `object.note` and `relation_type.color` were the only two differences, and `object.note` is never read by the merge code anyway). Since the whole merge runs in one transaction, this one missing column rolled back the entire merge, not just the relation-type rows. Fixed with a `hasColumn` guard, matching the existing pattern already used for `timeline_event.story`/`hashtag.tag_color`.
  - Fetched and statically compared the `v.2.7.3-dracondex` branch's `src/db/core.js` schema too — its `project`/`world_project`/`game_project`/`write_project` legacy tables match current schema column-for-column, so that era should already import cleanly via the existing `hasTable`/`hasColumn`-gated merge code once the two bugs above were fixed.
  - Verified directly: wrote a standalone Node script stubbing `electron` (mirroring `web-driver.mjs`'s own approach) to call `importDatabaseMerge()` against both real sample files in isolation — both now import successfully (`novel-manager 1.1.0.db`: 118 projects/86 objects/13 relation types merged; `dracondex 1.2.2.db`: 120 projects/144 objects merged), confirmed the original files were untouched (`git status` clean) and no temp files were left behind. Then seeded a `run-dracondex` scratch data dir with one merge's output and drove the full choice-modal → `chooseImportAsNexusNest()` path live: confirmed a real, browsable v3 module tree (120 `manager` modules, nested classifiers/inspectors with real Thai object names) came out the other end.
- No renderer/UI work was needed for the "choose Nexus Nest vs. Import DB" flow itself — it already existed and already worked for legacy-shaped data regardless of source version; it just never got a chance to run because the merge was crashing/rolling back on genuinely old files before reaching that point.

**Part 2 complete** — all 3 items (nav icon bug, view-only enforcement, sample-file import compatibility) live-verified: the WAL-crash and column-mismatch fixes were confirmed against the real `old_db_data/` sample files directly (not synthetic test data), and the nav-rail/read-only fixes were confirmed live via `run-dracondex`'s `web-driver.mjs`.

**`Plan.md` rollout complete** — Part 1 (hub polish, already committed as a mid-plan checkpoint) and Part 2 (cross-version DB import) both shipped and live-verified this session.

## Part 1 — Backend efficiency: data layer + boot (2026-07-25)

Shipped as `v.3.17.1` (`f62c854`). Files: `src/db/core.js` (the bulk), new `src/db/sqlscope.js`, plus `hashtag.js`, `hero.js`, `importdock.js`, `module.js`, `navigator.js`, `sage.js`, `timeline.js`, `versions.js`, `viewer.js`, `wiki.js`, and `src/renderer/core.js`.

The premise established up front and worth keeping in mind for anything that follows: with `node-sqlite3-wasm`, a statement executed **outside** a transaction pays its own file-lock cycle (~2.5ms) versus ~6µs inside one, and the SQL compile itself is noise by comparison (~1%). Every item below follows from that measurement — the lever is almost always "fewer lock cycles," not "faster SQL."

- [x] 1.0 **Perf instrumentation first, before touching anything** (`DDX_PERF` env) and cold/warm boot baselines captured, so every later claim could be checked against a real number rather than an intuition.
- [x] 1.1a **Prep refactor, deliberately behavior-free**: hoisted `DDL_SQL` / `INDEX_SQL` / `SEED_SYMBOLS` out of `initDB` and split `migrateInlineColumns()` off. Pure text movement, landed on its own so the next step's real change would stay bisectable.
- [x] 1.1b **Schema-version stamp via `PRAGMA user_version`**, hashed from DDL + index + migration text, so a boot whose schema already matches skips the redundant work entirely. Plus `PRAGMA cache_size=-8000` / `temp_store=MEMORY`, and the 48-row symbol seed wrapped in one transaction instead of 48 lock cycles.
- [x] 1.2 **Renderer boot: 7 serial awaits → 2 `Promise.all` waves** (`src/renderer/core.js`). The first await is what actually triggers `getDB()` to open the SQLite file and run `initDB()`, so it dominates — the later ones are cheap to parallelise around it.
- [x] 1.3 **Statement cache in `adaptDb`** — LRU of 256 keyed on the exact SQL string, with a stable `handles` map so `prepare()` returns the same object; `_reset()` in a `finally` keeps re-entrant use safe. Critically it is **gated off for the whole of `initDB`** (`setStatementCache(true)` only fires afterward) and flushed on close/DDL, so a cached statement can never outlive the schema it was compiled against.
- [x] 1.4 **~18 missing indexes**, including the composite `module_version(module_ref, seq)` and `import_file(nexus_ref, file_path)`.
- [x] 1.5 **New `src/db/sqlscope.js`** (`scopedAll`/`scopedGet`) plus sargable rewrites of the four hot closures (`quickIndex`, `getGraph`, `viewerIndex`, `sageHutStats`) and ~20 single call sites. The helper requires the `( ? IS NULL OR x.col=? )` pair to be the **first two bound params** and silently falls back to the original SQL otherwise — a constraint any later edit to those queries has to respect.
- [x] 1.6 **Wrapped the remaining un-transactioned write loops**; `syncWorldCategoryObjects` no-ops on an empty diff instead of rewriting rows to the same values.
- [x] 1.7 **Real bug fixed**: `PRAGMA foreign_keys=OFF` sat *inside* `importDatabaseMerge`'s transaction, where SQLite silently ignores it — so it had never actually taken effect.
- Also added while in `adaptDb`: `readTx(fn)` (a `transaction` wrapper whose name states the intent — one lock for a multi-statement read) and a `txDepth` guard making `db.transaction` **reentrant**, so a nested transaction joins the outer one instead of opening its own. Part 2 leans on both.
- Verified with `check.mjs` at the **0 errors / 31 warnings** baseline, a boot profile, a DDL-lock regression check, and `EXPLAIN QUERY PLAN` on the rewritten queries.

**Part 1 complete** — all 10 items shipped.

## Part 2 — Backend efficiency: IPC surface + renderer call sites (2026-07-26)

Files: `main.js`, `preload.js`, `src/db/{module,classifier,sage,wiki}.js`, `src/renderer/{core,hub,inspector}.js`, `src/renderer/mod/{classifier,manager,sagehut,fileviewer}.js`.

Part 1 fixed the data layer; the renderer was still issuing **one IPC round-trip per row** in several hot paths, each paying a structured-clone hop plus one of part 1's lock cycles on the main process. The work was measured rather than asserted: `ipcMain._invokeHandlers` was wrapped from the driver's `evalmain`, the same seeded vault was driven before and after (via `git stash`), and every flow below is a real counted number, not an estimate.

| flow | before | after |
|---|---|---|
| load a vault's nest tree | 10 IPC · **6 full re-renders** | 2 IPC · **1 render** |
| open a classifier module (12 objects) | 34 IPC | 6 (classifier + inspector portion: 30 → 4) |
| click all four Sage Hut tabs | 12 IPC | 3 |
| open a manager (5 children) | 13 IPC | 6 |
| render K display images | K IPC (base64 over the bridge, blocking `readFileSync`) | **0** |
| create one object | 35 IPC · 3 renders | 7 · 2 |
| delete one object | 35 IPC · 4 renders | 7 · 2 |

- [x] 2.1 **Batch IPC.** `classifier:getObjectsFull` collapses `4 + 2N` (a `getAttrs` **and** a `getObjectTemplates` per object) into one `readTx`, doing the `attrMap`/`conditionMap`/`privateTemplates` hydration db-side — the two per-object queries hit the same two tables for every object, so each becomes a single module-scoped pass. `module:getInspector` folds the Inspector's four parallel reads into one composite, keeping the `{attrs,tags,links,ui}` key names because `hub.js`, `mod/classifier.js` and `mod/manager.js` all read — and two of them *mutate* — `S.inspectorData` directly. `module:getAttrCounts` replaces Manager fetching every child's full attribute list just to read `.length`. **Deliberately deferred, not forgotten**: `object:getAttrsBulk`/`getTagsBulk`, `object:upsertAttrs` and the world-bulk channels all live in `director.js`/`navigator.js` — legacy modules already hidden from the nav rail — and were scoped out with the user's agreement rather than done blind.
- [x] 2.2 **Display images via a `ddx-file://` protocol** — `<img src>` points at it directly, so the bytes never cross the bridge and Chromium caches/revalidates them off the handler's ETag. Two things had to be got right. **The scheme is deliberately *not* `standard: true`**: `index.html` is loaded with `loadFile`, so the document origin is `file://`, and Chromium refuses to load a standard custom scheme as a subresource of a `file://` page — this was found by measurement, not by reading docs (the request never reached the handler at all and `<img>` fired `onerror`, silently falling through to the fallback; the first run looked like a success because the image *did* appear). A non-standard scheme is opaque-origin like `data:`/`blob:` and loads fine. **The URL carries a row id, never a path**: imported files are not copied into the data dir, so `import_file.file_path` is the user's original absolute path anywhere on disk and there is no prefix to sandbox against — accepting a path would have been an arbitrary-file-read hole. The handler serves only rows that exist and whose `file_type` is in the image allow-list. The `onerror` fallback batches every failed image in a tick into **one** `importdock:readFiles`, which is what keeps images working in the `run-dracondex` web-driver harness (no Electron protocol there); verified with 3 images + 1 nonexistent id → exactly 1 round-trip, unknown id degrading to the empty state rather than throwing.
- [x] 2.3 **Sage Hut** now fetches only the payload the clicked tab renders, memoised per nexus in `S.sageHutCache` — previously *every* tab click refetched all three, including `wiki:getGraph` (by far the most expensive) even when opening "Size". Also folded `sage.js`'s per-module `LENGTH(description)` loop — which re-`prepare()`d the same SQL once per module — into the module-list query that was already being run, as a `desc_bytes` column.
- [x] 2.4 **`wiki.js`.** `rebuildWikiIndex` and `resolveDanglingLinks` each got one outer transaction; because part 1 made `db.transaction` reentrant, the per-row transactions inside `reindexWikiLinks` collapse into it **with no call-site changes**. This matters most on the `initDB` backfill, which runs before `setStatementCache(true)` — the transaction is the only lever available on that path. `resolveWikiName` gained a memo scoped to **one bulk operation, never process-lifetime**: a long-lived memo would be an outright bug, since creating an entity retroactively changes a name that previously resolved to `null` (which is precisely what `resolveDanglingLinks` exists to handle). `resolveEntityKeys` went from one query per key to one `IN` per entity type, at **fixed arity 64 with the last chunk padded by a repeated id** — a variable-arity `IN` would mint a new SQL string per (prefix, arity) pair, churning part 1's string-keyed LRU and risking pushing the never-evicting `handles` map past its cap, degrading `prepare()` globally. Input order is preserved because `getBacklinks` hands the array straight to the UI.
- [x] 2.5 **Nest render storm.** `module:getNestItems` returns every content module's items for a whole nexus in one call, over the same five tables the old count query scanned. Rows are deliberately **light** — only the columns `ITEM_KIND[kind].nameOf` reads — because `SELECT *` would drag `book_chapter.chapter_content`, `timeline_event.story` and `chat_session.last_message` across IPC for an entire vault; opening an actual item still goes through the per-kind list-getter for the full row. Every content module gets an entry (empty ones get `[]`), which is what makes the old lazy per-module fetch a no-op rather than a re-fetch trigger, so the storm disappears structurally instead of being debounced. `scheduleNestRender()` coalesces the async re-render points into one per microtask, while `renderNexusHome()` itself stays synchronous so callers that read the DOM immediately after it keep working. `module:getItemCounts` / `getContentItemCounts` / `S.moduleItemCounts` were removed — the count is now just `.length`.
- **Two real bugs found and fixed along the way**, neither of them performance:
  - `S.displayImageData` was **never invalidated** — every invalidation point cleared only `S.displayImageCache` — so a file replaced on disk stayed stale for the whole session and the base64 blobs accumulated for the app's lifetime. Now `invalidateDisplayImages()` clears both, and the primary path holds no blobs in JS at all.
  - Registering the protocol unguarded **broke the web-driver harness outright**: it loads `main.js` with Electron's shell stubbed, so `protocol` is `undefined` and the whole file threw at load. Caught because the harness was actually run rather than assumed; both call sites are now guarded with `if (protocol)`.
- **A third defect was self-inflicted and caught before commit**: a stray NUL byte landed in the `resolveWikiName` memo-key separator, which git reported by flagging `src/db/wiki.js` as *binary*. Replaced with an explicit `::`, and every touched file was then scanned for stray control characters.
- **Verified live in real Electron via `run-dracondex`** (the web-driver path could not run here — Playwright's Chromium isn't installed on this machine — so the `onerror` fallback was exercised directly in Electron instead, and that limitation is stated rather than papered over). Correctness was established by **diffing payloads before and after against the same seeded vault**, not by eyeballing screens: per-module nest item counts, an object's `attrMap`/`privateTemplates`, `S.inspectorData`'s keys, Manager's attribute counts, all four Sage Hut statistics, backlink order, and the entire wiki index after a full `rebuildWikiIndex` — every one identical row for row, including dangling links still being dropped exactly as before. Screenshots were read (not assumed) for the nest tree, all four classifier views, all four Sage Hut tabs, a chronicler item page, and the display-image grid. `check.mjs` held at the **0 errors / 31 warnings** baseline throughout.
- **Deliberately left alone**: `openChronicler` still costs 6 IPC because `loadChroniclerData` is the module's own page loader, not the nest tree — out of scope for #2.5 and untouched on purpose.

## Part 1 — UI/UX pass: Sage Hut tabs, Hub accordion resize, nav-sidebar width
Files: `src/renderer/builder.js`, `css/layout.css`, `src/renderer/hub/tree.js`, `src/renderer/hub/sections.js`, `src/renderer/core/ui.js`, `src/renderer/core/state.js`, `css/tokens.css`, `css/nav-hub.css`

- [x] 1. Sage Hut — stop opening a new builder tab per sub-view (Size/Objects/Links/Graph)
  - Root cause: `builderPageKey` mints a distinct key per sub-view (`sagehut:dataSize`, `sagehut:objectAmount`, …), and `builderNavigate` (shared by every v3 pane opener — modules of all 15 kinds, Import Dock previews, item nodes) pushed any key not already in `pane.tabs`, so clicking through the four sub-views opened four separate tabs. Fixed by scoping a branch strictly to `ref.kind === 'sagehut'`: find any existing `sagehut:`-prefixed tab in the pane and overwrite it in place instead of pushing, leaving every other `ref.kind` on the original push-if-new path untouched.
  - `pane.active`/`pane.history` were deliberately left alone — back/forward navigation between sub-views still records and steps through each one; only the tab-bar entry stops multiplying, and it keeps its original position in the strip (in-place replace, not push-to-end).
  - Live-verified via `run-dracondex`: clicked Size → Objects → Links → Graph in one session and read `S.builder.panes[...].tabs` after each click — stayed at length 1 throughout (`["sagehut:dataSize"]` → `["sagehut:objectAmount"]` → `["sagehut:linkerList"]` → `["sagehut:linkerGraph"]`), confirmed visually (one "Sage Hut · …" tab in the strip). Also drove `builderBack()`/`builderForward()` through the same sequence and confirmed `S.sageHut.tab` still steps correctly (`objectAmount` → `dataSize` → `objectAmount`).
- [x] 2. Hub accordion sections (Nest / Sage Hut / Import Dock) — vertical drag-to-resize when more than one is open
  - Previously `#hub-body .acc-body{flex:1 1 0}` split remaining vertical space equally with no way to redistribute it. Reused the codebase's existing horizontal drag-resize idiom (`startLeftPanelResize`/`startInspectorResize`/`startPageViewResize` in `core/ui.js`) rather than inventing a new pattern — same mousedown → `document` mousemove/mouseup → localStorage-persist shape, just `clientY`/height instead of `clientX`/width. New `.panel-resize-handle-v` CSS modifier (reuses `.panel-resize-handle`'s hover/`is-resizing` styling, only overrides `width`/`height`/`cursor`). `buildAccSection` (`hub/tree.js`) takes an optional `heightPx` that becomes `flex:0 0 <px>` on the `.acc-body` (now tagged `data-key` so the resize handler can find the two live nodes); `buildHubHtml` (`hub/sections.js`) only applies stored heights and only inserts a handle between two sections that are **both open in the post-sort order** (so e.g. Nest+Dock open with Sage Hut collapsed still get a handle between the two that are actually adjacent on screen). New `startHubSectionResize` clamps each side to an 80px floor (matching `.acc-body`'s existing `min-height:80px`), persisted to a new `HUB_SECTION_HEIGHTS_KEY` localStorage key (`core/state.js`, alongside a `loadHubSectionHeights()` loader and `S.hubSectionHeights`).
  - Deliberately simple: no generic multi-pane splitter framework, just enough to resize the 3 known accordion sections; a section's stored height is inert while ≤1 section is open (nothing to redistribute against) and only takes effect again once a second section is opened.
  - Live-verified via `run-dracondex`: expanded all 3 sections (confirmed exactly 2 `.panel-resize-handle-v` elements, between nest/sage and sage/dock), dispatched a real `mousedown`→`mousemove`(+40px)→`mouseup` sequence on the first handle — Nest grew 193.7px → 233.7px, Sage Hut shrank 193.7px → 153.7px, Import Dock stayed untouched at 193.7px, and `localStorage['novel-manager-hub-section-heights']` recorded `{"nest":234,"sage":154}`. Re-ran `renderNexusHome()` afterward and confirmed the same heights (234/154/193) survived the re-render.
- [x] 3. nav-sidebar — reduce width by 25%
  - One-token change: `--nav:56px` → `--nav:42px` (`css/tokens.css`; `--sidebar` for the separate, independently-resizable Hub/left-panel is untouched). Confirmed theme-safe beforehand — no theme overrides `#nav-sidebar`'s width (only `rainbow` touches that selector, and only for `background`/`backdrop-filter`); `css/titlebar.css`'s `calc(var(--nav) + var(--sidebar))`/`calc(var(--nav) + 1px)` derive automatically.
  - Icon-overflow check caught a real fit problem before it shipped: `.nav-logo-btn` was 44×44px, which would overflow a 42px-wide rail (`#nav-sidebar` has no `overflow:hidden`). Shrunk it to 40×40px (`css/nav-hub.css`) to match `.nav-btn`'s existing footprint instead of inventing a third button size — `.brand-img` (30×30px) fits either box unchanged.
  - Live-verified via `run-dracondex`: screenshotted the narrower rail with icons centered and not clipped, and cross-checked the `rainbow` theme (the one theme restyling `#nav-sidebar`) still renders correctly at the new width.

**Part 1 complete** — all 3 items shipped and live-verified.

## Part 2 — Auto default "UI Size" from screen resolution
Files: `src/renderer/core/state.js`

- [x] 1. Auto default UI size by user resolution, from checking the user's screen size
  - `Plan.md`'s wording ("UI size") is an exact match to an existing Settings feature literally labeled that (`t('uiSize')` → Thai `'ขนาด UI'`, `S.settings.size`, a 50–200% renderer zoom applied via `document.body.style.zoom` — distinct from the separate "Font Size"/`fontScale` slider, confirmed by reading `uiSizeSlidersHtml()` which renders both side by side with different labels/ranges). Previously `loadUiSettings()` defaulted `size` to a flat `100` whenever nothing was saved yet; new `autoUiSizeFromScreen()` computes that first-run default from `window.screen.width` instead — baseline 1920px == 100%, scaled proportionally, rounded to the nearest `UI_SIZE_STEP` (5), clamped to 80–130 (the same safety band `fontScale` already uses elsewhere in this file, narrower than the manual slider's full 50–200 range so an unusually small or huge monitor can't silently produce an illegible or absurd auto default — the user can still push further via the slider).
  - Renderer-only: `window.screen.width` is a plain DOM API, unaffected by `contextIsolation`/`nodeIntegration` — no IPC or `main.js`/`BrowserWindow` change needed. No new persistence; the computed value only becomes "saved" once the user touches the slider, same as the old flat-100 default.
  - Live-verified via `run-dracondex`: on the driver's actual 1920px-wide screen, `S.settings.size` resolved to `100` (matching the old default exactly, confirming no regression at the common resolution) and `autoUiSizeFromScreen()` returned `100` directly. Sanity-checked the formula's clamping at other widths by evaluating the same arithmetic: 1366px → 80 (clamped up from ~71), 2560px → 130 (clamped down from ~133), 800px → 80 (clamped up from ~42).

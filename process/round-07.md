## Part 1 — Nexus Nest tree polish + VS-Code-Explorer CSS tightening

Landed in commit `074cb29` (v.3.10.1), before this session started. Two areas:

- **Nest tree row polish** (`src/renderer/hub.js`, `src/renderer/core.js`): a new "Nexus Nest options" popup (`openNestOptionsPopup`/`buildNestOptionsPopupHtml`, driven by 4 new `S.settings` flags — `nestShowItems`, `nestShowMajorIcon`, `nestShowMinorIcon`, `nestSignatureMode`) toggles: whether content-item leaves show under their owning module at all, whether a module's own icon renders, whether a content item's icon renders, and whether the tree's trailing kind badge shows the kind name or its icon. The old always-visible decorative `.grip` drag-handle span was removed — `draggable="true"` moved onto the whole `.li` row itself (name/icon/background all now start a real drag, not just a ~10px sliver). A module whose only children are content items (no nested module children) now gets a `+`/`-` glyph pair instead of the expand caret, since it has nothing to "descend into," only items to reveal.
- **VS-Code-Explorer CSS tightening** (`style.css`): `.acc-head`, `.li`, `#left-panel-inner`, `#left-panel-foot`, `#search-bar`, and `.nexus-vault-head` all had their padding cut from the original ~8-12px down to 1-2px (plus removing several now-redundant margins), matching Plan.md's ask to visually match VS Code's Explorer density. `.ph.nexus-vault-head` got a scoped override rather than touching the shared `.ph` rule (used by 40+ other panel headers app-wide).

**Part 1 complete** — verified live in the same session that authored it (commit message references live testing); not re-verified this round since untouched by Parts 2-3.

## Part 2 — Hub page: Kind Browser own page + legacy-import rework

Files: `src/db/core.js`, `src/db/migrate_v3.js`, `src/db/director.js`, `main.js`, `preload.js`, `src/renderer/hub.js`, `src/renderer/core.js`, `src/renderer/builder.js`, `src/renderer/mod/{fileviewer,item,sagehut}.js`, `src/renderer/i18n.js`.

- [x] **Kind Browser promoted from a Hub accordion section to its own full page.** Removed the `{key:'kinds', ...}` entry from `buildHubHtml()`'s accordion array (`hub.js`). New `S.kindBrowserPage` flag, `goToKindBrowserHub()` (mirrors `goToNexusNestHub()`'s reset-and-render pattern), `buildKindBrowserPageHtml()` (a `.detail-head` header + the unchanged `buildKindBrowserHtml()` body), and a new nav-rail button (second icon, right after Home) in `renderModuleRail()`. Every other view-opener (`openModuleNode`, `openImportFile`, `openItemNode`, `openSageTab`, `builderOpenPage(null)`, `clearWorkspaceTabs`) got `S.kindBrowserPage = false` added to its existing mutual-exclusion reset, so the rail button's `active` highlight and the page-precedence chain in `buildBuilderPageHtml()` (core.js) stay correct. Live-verified via `run-dracondex`: full-page render confirmed (not accordion), grouping/counts intact, Hub no longer shows the "browse by kind" section.
- [x] **Legacy Import accordion removed; replaced by a modal-driven Nexus-Nest-vs-Import-DB choice.** `ensureLegacyImport`/`buildLegacyImportRows`/`runLegacyImport` deleted outright (confirmed unused after the accordion entry was removed) along with the now-dead `S.legacyImport` state. New `openImportChoiceModal()`/`chooseImportAsNexusNest()`/`chooseImportAsDb()` (`hub.js`), triggered from `importDatabaseFile()` (`core.js`) after a merge whose `summary` shows any un-migrated legacy rows. `MIGRATE_TARGETS` (`hub.js`) extends the pre-existing `ARTISAN_TARGETS` (director/navigator/hero/writer) with `scribe`, which has no legacy "project" table of its own.
  - **Prerequisite bug found and fixed first**: `importDatabaseMerge` (`src/db/core.js`) only ever merged Director-shaped legacy tables — no merge blocks existed for `world_project`/`game_project`/`write_project` or the `relation`/`relation_obob`/`relation_obtl`/`relation_tltl` edge tables. Added full merge blocks for all three (Navigator's `world_character`/`world_orig_*`/`world_timeline_*`, Hero's `game_char_*`/`game_col_*`/`game_story`+dialogue graph, Writer's `write_series`→`write_book`→`write_chapter`+`write_note`→`write_chat`) plus the Director relation-instance tables, using the same natural-key-matching idiom the existing Director blocks already used. Deliberately left the purely-referential cross-link tables unmerged (Navigator's `world_map`/`world_character_link`/`world_timeline_object`, Hero's `game_cat_object`/`game_char_element`, Writer's `write_wiki_link`/`write_word_link`/`write_novel_link`) — a documented scope simplification, not an oversight.
  - **"Import as Nexus Nest"** reruns `src/db/migrate_v3.js`, substantially rewritten: every migrated object/event/area is now a real child `module`-table row (kind `inspector`, freeform-markdown body built from the legacy typed attributes) instead of the old lightweight `classifier_object`/`timeline_event` content-item rows — a deliberate fidelity trade-off confirmed with the user (objects lose typed/searchable fields, gain a real Nest-tree presence). Director's `relation`/`relation_obob`/`relation_obtl`/`relation_tltl` rows now migrate into a real `connector` module (`mkRelationConnector`) whose `filterDef.moduleIds` scopes to that project's own classifier/chronicler modules and whose edges are real `entity_relation` rows (`src/db/viewer.js`'s `createEntityRelation`) — not a synthesized-wikilink hack. Navigator gets no connector of its own; if a Director connector already exists in the same migration batch (tracked via a `batchCtx` object threaded through every `migrateLegacy` call — mutated in the main process, handed back in each response since IPC args serialize by value), Navigator's new classifier/chronicler ids are folded into it instead. Scribe (new target) walks `note_folder` into a `collector` tree (1:1, no `manager` wrapper — no legacy "project" concept to justify one) with `note` rows becoming `inspector` modules; required a new `note.migrated_v3` column (bulk-flagged per nexus, not per-row like the other 4 targets). Writer's `write_note` migration had a pre-existing bug (passed `null` as content, since the actual markdown lives in child `write_chat` rows) — fixed in the same pass. Live-verified via `run-dracondex`: seeded a Director project/category/object, opened the real modal (real translated text, not raw i18n keys), ran the migration, and confirmed via `module.getTree` a real `manager → classifier → inspector` chain; separately verified a project with an OBOB relation produced a `connector` module with a real rendered graph edge.
  - **"Import as Import DB"** — new `S.importDbMode` flag, `openImportDbHub()` (calls the existing unchanged `selectModule('director')`), a new always-static nav button (`#btn-import-db-hub`, `index.html`) un-hidden only in this mode by a one-line change to `updateTopNavButton()`'s legacy-button-hiding regex, and reset at every existing `returnToNexus()`/`clearWorkspaceTabs()` exit point. Read-only enforcement could **not** be a renderer-side monkey-patch of `window.api.<ns>.<fn>` as first planned — Electron's `contextBridge.exposeInMainWorld` deep-freezes the exposed object, so reassigning its properties from renderer-world code silently no-ops (or throws, in strict-mode files). Moved the guard into `preload.js`'s own isolated scope instead: a module-scoped `importDbMode` flag (toggled via a new `api.setImportDbMode(bool)` the renderer calls on enter/exit), and `inv()` itself rejects any non-`get*` channel in the legacy namespaces (`project/category/template/object/timeline/map/relation/world/game/write/hashtag/color` — confirmed exhaustively against main.js's real channel list that "block everything except `get*`" has zero false positives/negatives for these namespaces specifically). A new `unhandledrejection` listener (`bindGlobalShortcuts`, core.js) turns the rejection into a visible toast, since the legacy Director/Navigator/Hero/Writer save handlers this view reuses unchanged don't all wrap their `api.*` calls in try/catch.
  - **Bug found during live verification, fixed same session**: the Import DB view initially showed "0 รายการ" for a category that had a real seeded object. Root cause: `database.js` spreads `...director` then `...classifier` into one flat exports object, and both files exported identically-named functions (`getObjects`, `getObject`, `createObject`, `updateObject`, `updateObjectNote`, `deleteObject`, `getTemplates`, `createTemplate`, `updateTemplate`, `deleteTemplate`, `upsertAttr`) — classifier.js's v3-shaped versions silently shadowed Director's legacy versions ever since classifier.js was added, so Director's own `object:*`/`template:*` IPC handlers were calling classifier's module-tree-shaped implementations under Director's project/category-shaped arguments (`object:create` threw a FOREIGN KEY error; `object:getAll` returned nothing). Pre-existing bug, latent because Director's UI was nav-rail-hidden this whole time — newly reachable because the read-only Import DB view is the first real path that un-hides it. Fixed by renaming director.js's 11 colliding exports with a `dir` prefix (`dirGetObjects`, `dirCreateObject`, etc., including the exported property names, not just the internal identifiers) and updating main.js's `template:*`/`object:*` handlers to call the renamed functions; classifier.js and its own `classifier:*` channels were untouched. Re-verified live end-to-end: the same seeded object now shows correctly in the read-only view, the read-only guard still blocks a create attempt with the correct toast, and a v3 Classifier module's own object-create flow (unrelated to this fix) still works normally.
  - i18n: 8 new keys (`importChoiceTitle/Body/NestOption/NestDesc/DbOption/DbDesc`, `importDbHubTitle`, `importDbReadOnly`) added across all 18 locale blocks.

**Part 2 complete** — both items shipped and live-verified via `run-dracondex`, including one pre-existing bug found and fixed along the way (director/classifier export collision) and one implementation-approach correction made before shipping (the read-only guard had to move from a renderer-side monkey-patch, which doesn't work under `contextBridge`, to a preload-level channel guard).

### Part 3 — Chronicler module: One-line zoom bug + event inspector
- [x] 1. One-line view zoom bug — the event dot visually drifted away from its own tick/label when zooming
  - Root cause: `updateTimelineGraphX()` (`src/renderer/timeline.js`) repositioned `[data-event-dot]` circles on every wheel-zoom, but the per-event tick connector `<line>` and name/date `<text>` elements built in `buildChroniclerOneLineHtml` (`src/renderer/mod/chronicler.js`) carried no `data-*` attributes at all — they never moved, so the dot drifted away from its own label as the user zoomed. Fixed by adding `data-event-tick`/`data-event-label`/`data-event-date` (each carrying the same `data-start-ts` key the dot already used) and extending `updateTimelineGraphX()`'s reposition pass to include them.
- [x] 2. One-line view — event inspector below the graph, editable
  - Clicking an event's dot no longer opens the old full modal — it calls `toggleChroniclerInspector(tlid, evId)`, which renders an inline, editable panel (name/start date/end date/color/story) below the graph via a new shared `buildChroniclerEventInspectorHtml(ev, tlid)`. Clicking the same dot again (or the panel header's close button) closes it.
  - [x] 2.1. Downline view — same inspector as a per-row dropdown, autosave
    - Each row in `buildChroniclerEventListHtml` expands into the same shared inspector body when clicked, instead of opening the modal. Text/date fields autosave via `onchange="saveChroniclerInspectorField(...)"` (added an optional `onchangeFn` param to `dateInputsHTML`, `src/renderer/modals.js`, default `''` — backward compatible with every other existing caller); the color picker autosaves via a separate delegated click listener (`bindChroniclerInspectorColor`) instead, since the shared `colorPicker()`/`pickColor()` widget sets its `#sel-color` hidden input by direct property assignment rather than firing a native `change` event — a plain bubble-phase click listener still reads the correct value, because `pickColor`'s synchronous prefix (everything before its first `await`) has already written it by the time the click event finishes bubbling.
  - [x] 2.2. Downline view — only one inspector dropdown open at a time
    - Enforced structurally, not just by convention: `S.chroniclerData.inspectorEventId` is a single id (not a Set), so opening a new row's dropdown always replaces whichever one was open — this is a hard requirement, not only a UX choice, since `colorPicker()` renders singleton DOM ids (`#sel-color`, `#cpicker-grid`, `#cpicker-native`, `#cpicker-recent`) that two simultaneously-open instances would collide on.
  - No new i18n keys needed — every inspector label reuses existing translation keys (`name`, `startDate`, `endDate`, `color`, `story`, `saved`, `close`) already present in all 18 locales.
  - New CSS: `.chr-insp-row`, `.chr-insp-body` (`style.css`).
  - Live-verified via `app-run-tester` against real Electron: created a fresh module of kind `chronicler`, one timeline line, 5 events spanning 1000–2000 CE. Confirmed before/after-zoom screenshots show each dot's tick+label staying aligned with its dot; confirmed the One-line inspector opens/edits/persists (renamed an event, confirmed via `eval window.api.timeline.getEvents(...)`, and saw the graph's own label update on reopen) and closes on a second click; confirmed the Downline dropdown opens per row, autosaves a story-field edit (again confirmed against the DB), and that opening a second row's dropdown collapses the first (`document.querySelectorAll('.chr-insp-row.open')` returned exactly one element throughout); confirmed clicking the small dot on Downline's left-side graph toggles that same row's dropdown in the list on the right.

### Part 4 — Theme the app's native `<select>` dropdowns
- [x] 1. Every white/native dropdown selection box in the app — restyle to match the active theme
  - Root cause: this codebase styles `<select>` entirely via specific class/context selectors (`.fg select`, `.form-row select`, `.settings-select`, `.rel-toolbar select`, `.qs-filters select`, …) — there was no generic base rule at all. Many `<select>` elements across the v3 module renderers and modals sit outside every one of those wrappers (e.g. Chronicler's own `#chr-line-select`/`#chr-compare-select`, plus bare selects in `hero.js`, `navigator.js`, `modals.js`, `scribe.js`, `quickswitch.js`, `relation.js`, `writer.js`, `designer.js`, `fileviewer.js`, `wanderer.js`, `sketcher.js`, `viewer.js`), so they fell through to the browser/OS-native white dropdown regardless of the active theme.
  - Fixed with one base rule (`select{...}`, `style.css`, placed directly after the `body{}` block): themes `background`/`color`/`border` off `--surface`/`--t1`/`--border`, plus `:focus`/`:disabled` states and a `select option{...}` rule. Chromium (Electron's renderer) does honor `background`/`color` on `<option>`, including inside the native popup list, unlike some other engines. The existing more-specific class rules (`.fg select`, etc.) keep winning by CSS specificity exactly as before — this is a themed fallback for every `<select>` that previously had no rule at all, not a replacement for the specific ones.
  - Live-verified: injected a bare probe `<select>` via `eval` into the running app and read `getComputedStyle` — matched the active (dark) theme's `--surface`/`--t1`/`--border` (`rgb(24,24,31)` / `rgb(232,232,240)` / `rgb(46,46,63)`) by default, then correctly switched to the `daylight` theme's own white-surface convention (`rgb(255,255,255)` / `rgb(23,32,51)`) after setting `data-theme="daylight"` — confirming the dropdown now tracks the active theme instead of being hardcoded to native white. `check.mjs` full sweep: 0 errors, the same 33 pre-existing warnings as before this round (none new).

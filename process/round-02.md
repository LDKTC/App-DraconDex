### Part 1 — เพิ่มfeature (add)

- [x] 1. Nest hub — drag-and-drop auto-move when a module leaves/enters a Parent, or is dropped onto another module
  - `onNestDrop` (`src/renderer/hub.js`) had an `isLockedToParent` branch: a module that already had a parent could only reorder among its existing siblings via drag — reparenting across parents required the "Move to…" context-menu item instead. Removed the restriction entirely; the pre-existing `isSelfOrDescendant` guard (can't drop into your own subtree) is the only rule left. `api.module.move`/`src/db/module.js`'s `moveModule` already supported arbitrary reparenting with no depth assumption, so this was purely a UI-layer restriction, not a backend change.
  - Live-verified via `web-driver.mjs`'s new `dragto` (real mouse down/move/up, not synthetic events): dragged a nested child module onto a *different* top-level module's row (nest zone) — it became that module's child (confirmed via `S.moduleTree` structure); then dragged it back out onto a top-level row's edge (reorder zone) — it returned to top-level. Both directions worked in one pass.

- [x] 2. Nest hub context menu — clicking a module shows a "Create" button whose hover reveals the module kind-list as a submenu; move the create-list that used to sit on top of the context menu into that submenu
  - `buildModuleContextMenuHtml` (`hub.js`) used to inline `buildKindListHtml(null)` (all 15 kinds, creating a new top-level sibling module) directly at the top of a Major-module's context menu. Replaced with a single `.kli-submenu-parent` "Create" row (reuses the existing `create` i18n key already present in all 18 locales — no new key needed) that opens a second floating `.kind-popup.ctx-submenu` on `mouseenter` (`openCreateSubmenu`, positioned to the row's right edge via new `positionSubmenuNear`, flipping left if it would overflow the viewport), closed on `mouseleave` via a 200ms grace timer (`scheduleCtxSubmenuClose`/`cancelCtxSubmenuClose`) so crossing the gap to the flyout doesn't close it prematurely. Same top-level-creation semantics as before (`parentId=null`), just relocated into the submenu rather than flattened inline. New CSS: `.kli-submenu-parent`, `.kli-arrow`, `.ctx-submenu` (`style.css`).
  - Live-verified via `web-driver.mjs`'s new `rclick` (real right-click) + a dispatched `mouseenter` on the "Create" row: screenshotted the menu (single "สร้าง ›" row, no more flat 15-item list), then the open submenu (all 15 kinds rendered), then clicked "Sketcher" — confirmed a new top-level `sketcher` module was created and every `.kind-popup` (menu + submenu) closed cleanly.

- [x] 3. Nav-sidebar — add a button to open/return to the Nexus Nest hub
  - `#nav-logo-btn` (index.html, static) already flips to a "return" icon and calls `returnToNexus()` when `S.activeModule` is set, but that only covers legacy full-page modules (Director/Navigator/Hero/Writer/Sage/Artisan/Scribe) — drilling into a v3 module node inside the Builder (`S.activeModuleNode` set, `S.view` still `'nexus'`) had no one-click way back to the Hub home. Added a `home` icon to the `I` icon object (`src/renderer/core.js`, simple house glyph matching the existing SVG conventions), a `goToNexusNestHub()` function (`hub.js`: clears `S.activeModuleNode`/`S.filePreview`/`S.sageHut`, then `renderNexusHome()`), and wired it as the *first* button in the dynamic nav rail (`renderModuleRail`, before "+create") so it's always in the same place regardless of pinned-module count. It lights up `active` whenever the Hub welcome page is showing.
  - Live-verified: opened a real module (Sketcher, a non-collector kind so it actually focuses — collector modules just toggle expand/collapse and never set `S.activeModuleNode`), confirmed the home button was unselected while the module's detail page + tabs were showing, clicked it, confirmed `S.activeModuleNode` went back to `null`, the main pane returned to the vault welcome page, and the home button lit up active again — while the open tab stayed in the tab strip (deselect, not close).

### Part 2 — แก้feature (fix)

- [x] 1. Scribe — opening it then returning to the Nexus Nest leaves a Scribe pane stuck below the Builder pane, uncloseable
  - Root cause, found by direct reproduction rather than guesswork: `renderBuilderPanes`'s `pruneStaleLayoutElements` (`src/renderer/builder.js`) only ever removed *stale* `.bpane`/`.bsplit` elements (ones no longer in the current layout tree) from `#main-inner` — it never touched *other* leftover children. Any legacy view that wholesale-replaces `#main-inner.innerHTML` directly (Scribe, Director, the Nexus picker, and others) leaves that markup sitting there forever once `ensureNodeElement` starts `appendChild`-ing fresh `.bpane` nodes back on top of it when the Builder grid re-renders — there was never a full clear, only incremental prune-and-append. Fixed by sweeping any child of `#main-inner` that isn't `.bpane`/`.bsplit` out inside `pruneStaleLayoutElements`, once, before the grid (re)renders.
  - Live-verified twice: first reproduced (pre-fix) via the Nexus-picker → nexus-home transition — two stacked "welcome" panes appeared, the old one uncloseable, exact same mechanism as the reported Scribe bug. Then, after the fix, drove the *actual* reported path: `selectModule('scribe')` → `returnToNexus()`, and confirmed via `Array.from(document.querySelector('#main-inner').children)` that only the fresh `.bpane` remained — no leftover Scribe markup.

- [x] 2. Hub — an unopened section shouldn't be "replaced"; keep original order, opens push to the top, closes sink to the bottom, bottom-most (e.g. Import Dock) sits flush against the nexus-vault-head bar below
  - Investigated fresh rather than assumed: `buildHubHtml`'s existing stable sort (`sections.sort((a,b) => (S.hubOpen[b.key]?1:0) - (S.hubOpen[a.key]?1:0))`) already does exactly this — open sections keep their original relative order at the top, closed ones keep their original relative order at the bottom — and was in fact already shipped in a *previous* round (the code comment still reads `Plan part1 #2`). `#left-panel-foot` (the nexus-vault-head bar) is a fixed flex sibling directly below `#left-panel-inner`, so whatever ends up visually last inside the hub body is automatically flush against it with no separate handling needed.
  - Live-verified fresh (not assumed from the old comment): toggled Nest/Sage Hut/Import Dock open and closed in several orders via `toggleHubSection`, reading `#hub-body > .acc-head` text order after each toggle — matched the spec exactly in every combination tried (single open, two open, closing the previously-topmost one). Screenshotted the all-collapsed state and confirmed the bottom-most collapsed header sits directly against the "TESTVAULT" vault-head bar with no gap. **No code change was needed** — checkbox ticked on the strength of this fresh verification, not a fix.

- [x] 3. Hub — give each section (Nest / Sage Hut / Import Dock) its own separate container/content-box/scrollbar instead of one shared one
  - Confirmed the intended scope with the user first: independent scroll *per open section* (sections sharing the available height equally, not a fixed max-height or a no-op). `#left-panel-inner{overflow-y:auto}` (`style.css`) was the single shared scrollbar for the whole Hub body; it's also reused by non-hub views (nexus picker, project sidebar, etc.), so the fix is scoped entirely to markup that only exists while the Hub renders. `#hub-body` (`buildHubHtml`, `hub.js`) is now a flex column (`display:flex;flex-direction:column;height:100%`, new CSS scoped to `#hub-body`/`#hub-body .acc-head`/`#hub-body .acc-body`); each open section's `.acc-body` gets `flex:1 1 0;overflow-y:auto;min-height:80px` so multiple open sections share the remaining vertical space equally and each scrolls independently, while a collapsed section stays `display:none` (unchanged, already inline) and consumes no flex space. `#left-panel-inner`'s own `overflow-y:auto` stays in place untouched as a harmless fallback — in normal use `#hub-body`'s `height:100%` means it never actually needs to fire.
  - Live-verified: created enough top-level modules to overflow the Nest section, opened all three sections at once, confirmed via `scrollHeight`/`clientHeight` that all three `.acc-body` elements got equal `clientHeight` (164px in the test window) with only Nest actually overflowing; then set Nest's `scrollTop` directly and confirmed Sage Hut's, Import Dock's, and the outer `#left-panel-inner`'s scroll positions all stayed at 0 — genuinely independent, not just visually separated. Screenshotted before/after the scroll to confirm Sage Hut/Import Dock content stayed put on screen.

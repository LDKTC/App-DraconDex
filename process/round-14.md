## Part 1 — Cloud Sync Function (Supabase/Google/Firebase/Github) + Setting window rework (v4.0.0)

Four independent Cloud Sync sub-features plus a full Setting window rebuild, done across several sessions and folded into one `v.4.0.0` commit. Detail below is reconstructed from `docs/CHANGELOG.md`'s per-feature entries (this work predates the current conversation), each of which was itself written and live-verified at implementation time.

- [x] **Supabase — Cloud Sync → Token Sync.** Replaced the old permanent access-key prototype (v3.8.0) with a 16-digit token minted fresh on every push. Added Google login via Supabase Auth (PKCE + loopback redirect) as a hard prerequisite for uploading. Upload quota now varies by account tier (`sync_account.tier`: free 1 slot/10MB, pro 3 slots/20MB — the user changed the spec mid-plan from "20MB for every account" to this two-tier split). Added an optional per-slot password (hashed with `pgcrypto`, skippable when the pulling account matches the uploading account, 8 wrong attempts locks the slot 15 minutes) and a 72-hour expiry checked on read. The old owner/read-key model (`sync_key` table + its RPCs) was dropped outright — the Google account now does the authentication job that table used to do. Files: `src/db/sync.js`, `src/db/sync-devserver.js`, new `supabase/migrations/20260730000000_dracondex_token_sync.sql`, `src/renderer/sync.js`, `main.js`, `preload.js`, `css/builder.css`, 18-locale i18n keys. Docs rewritten at `docs/SYNC.md`.
- [x] **Google — Drive Backup.** New opt-in backup path through the user's Google Drive `appdata` folder, independent of Supabase (Supabase Auth doesn't auto-refresh provider tokens, so bundling the two logins would have forced every Cloud Sync user to also grant Drive access they never asked for — researched and rejected before building). Backs up the "layout profile" (theme/language/UI-size from localStorage) and/or the `.ddx` database file, each toggle independent, reusing the existing `exportDatabaseTo`/`importDatabaseMerge` functions rather than writing a parallel export path. Auto-backup runs hourly on a renderer-side timer; the status bar warns/blocks as Drive space runs low/full. New files: `src/db/oauth-loopback.js` (pulled out of `sync.js`), `src/db/drive.js`, `src/db/drive-devserver.js`, `src/renderer/drive.js`. Docs: new `docs/DRIVE.md`.
- [x] **Firebase — version notice.** Reads one public Firestore document (`public_config/latest_version`, no credential needed) and does a simple string compare (stripping any `-n` suffix first) for users logged into either Cloud Sync or Drive Backup. Deliberately **not** an auto-updater — this app has no publish/release pipeline (no `electron-updater`, no GitHub Releases in real use), so the scope is a notice plus a button that opens the download page in the system browser, remembering the last version it already nagged about so it doesn't repeat. New files: `src/db/update.js`, `src/renderer/update.js`. Docs: new `docs/UPDATE.md`.
- [x] **Github — sandboxed extension downloads.** Extensions are pulled from a GitHub repo carrying a `dracondex-extension.json` manifest at its root; each one declares its own database table (`ext_<id>_<name>`, TEXT/INTEGER/REAL columns only) and runs in a dedicated `BrowserWindow` with its own preload (`preload-ext.js`, no `window.api` exposed at all — only `window.extApi.table.*`, whose ownership is bound to the window itself rather than trusted from a caller argument). No raw-SQL passthrough anywhere; every table/column identifier goes through a freshly-written whitelist since no existing prepared-statement pattern could bind a table/column name. **Root cause investigated before building**: `contextIsolation` on the main window only blocks direct Node/Electron access, it does not sandbox one script in a page from another script in the same page — so an extension loaded into the main window would have had the app's own full read/write/delete rights over every Nexus. The separate-window-plus-separate-preload design exists specifically to close that gap. **Accepted limitation, not silently glossed over**: there's no real OS-level Chromium sandbox, because `main.js` already runs the whole process with `--no-sandbox` for the portable build — every window, extensions included, is equally affected by that pre-existing constraint. No code review of GitHub-sourced code happens before install either. New files: `src/db/extension.js`, `preload-ext.js` (repo root), `src/renderer/extension.js`. Docs: new `docs/EXTENSIONS.md`.
- [x] **Setting — Quick Setting popup + full Setting window.** Quick Setting popup cut down to exactly 4 items per `Plan.md` (language, module name-display mode, UI size, an "open full settings" button) — replacing what used to be a much larger Preferences panel. That panel is gone entirely, replaced by a real two-level Setting window (group → page: Workspace/User/Appdata/Extension, each with its own sub-pages) built via a `registerSettingPage(group, page, fn)` registry that lets each feature's own file own its page instead of one monolithic settings file. New "Tool toggle" page controls what reappears in the Quick Setting popup / nav-sidebar quick buttons / status bar. New "Account"/"User profile" page (multiple named layout slots stored in Drive `appdata`, separate from the hourly auto-backup file). New "Database" page (export/import at both whole-Nexus and single-module granularity, reusing the same snapshot format Token Sync already serializes with — `serializeVault` gained a `moduleIds` param, and `applySnapshot` was split into a reusable `applySnapshotCore` plus a new `importModuleSnapshot` for the module-scoped case). New files: `src/renderer/core/setting-window.js`, `tool-toggle.js`, `account.js`, `db-transfer.js`, plus `src/db/db-transfer.js`. New regression test `test/module-transfer.test.mjs`. 51 new i18n keys across all 18 locales. Docs updated: `docs/SYSTEMS.md` §Setting Window, `docs/DRIVE.md`, `docs/EXTENSIONS.md`.

**Part 1 complete** — all 5 sub-items shipped, each live-verified in the running app at implementation time per its own `docs/CHANGELOG.md` entry.

## Part 2 — New Workspace: Wyvern, Drake, Dragon, and the Settings picker (v4.1.0)

Three selectable app layouts, built across two sessions. Wyvern shipped first as its own checkpoint commit (`c99db0b`); Drake's selectability, Dragon (built entirely this session), and the Settings picker that ties all three together shipped together to close out Part 2.

- [x] **Standard workspace — Wyvern** (from `featureplan.md`'s spec, previous session — reconstructed from `docs/CHANGELOG.md`/`docs/SYSTEMS.md`, not this session's own memory). The newcomer/simple layout: hides `#nav-sidebar`/left-panel Nest tree/tab strip/split-layout picker (mirroring `.popup-mode`'s hide-list but keeping Settings + status bar visible), replaced with a thin vertical `#workspace-toolbar` (`src/renderer/wyvern.js`) carrying Views/Import/Export/Hashtag/Color/Create-module buttons that all call Drake's existing functions verbatim. Drill-down browsing (`buildWyvernBrowseHtml`/`wyvernDrillInto`/`wyvernDrillUp`, breadcrumb + card grid) replaces the left-panel tree entirely — a module with children drills in, a childless one opens its detail page. No split panes, no auto-tab: `S.builder.layoutTree.type` stays `'leaf'`, `pane.tabs` stays empty for this style. Live-verified via `run-dracondex` at the time, including a Drake regression pass confirming the new `workspaceStyle==='wyvern'` guards left Drake's own behavior untouched. Left un-shippable for real users: no UI to actually pick it (only `?workspace=wyvern` for testing) — that gap is what this session's Settings page closes.
- [x] **Studio workspace — Drake** (this session). Required zero new behavior — Drake already *is* the current UI (nav-sidebar + left-panel Nest tree + split-pane Builder) and was already the unconditional default before this Part existed. The only real work was making it a genuine, equal option in the new Settings picker rather than an implicit fallback, and re-confirming — this time through the picker itself, not just the query param — that switching to it and back produces zero regression.
- [x] **Sandbox workspace — Dragon** (this session, entirely new). Direction was confirmed with the user ahead of implementation, since `Plan.md`'s own spec for this item was deliberately open-ended (only "don't duplicate the other two", "user freedom", "reuse the nexus-nest architecture but render it flexibly", optionally not a single window, floating "Bookshelf/Library style" as one idea): a **freeform spatial canvas** — modules as cards the user drags to arbitrary positions on a board, closest in spirit to the existing `mod/designer.js` free-diagram board.
  - `src/renderer/dragon.js` (new): `buildDragonCanvasHtml()`/`mountDragonBoard()` render each module as a `.dragon-card` and wire pointerdown/pointermove/pointerup drag directly mirroring `mod/designer.js`'s own free-drag implementation (a `moved` flag distinguishes an actual drag from a plain click) — deliberately not HTML5 `dragstart`/`drop`, which doesn't suit arbitrary x/y placement. `renderDragonHome()`/`buildDragonPageHtml()` hook into `renderNexusHome()`'s existing workspace-style branch exactly the way Wyvern's own entry point does, deferring to `buildBuilderPageHtml()`/`KIND_MAIN_BUILDER` for actual module content — Dragon never reimplements how a module renders once opened, only how the tree gets browsed.
  - **Chrome differs from Wyvern on purpose**: `Plan.md` explicitly wants Dragon to "show tools as before" (`แสดง tool ตามเดิม`), so `#nav-sidebar` stays fully visible (import/export/hashtag/color etc.) — only `#left-panel`/`#left-panel-resize`/`#builder-tabs`/`#layout-menu-wrap` hide. Dragon has no dedicated toolbar element at all, unlike Wyvern.
  - **Drill-down mechanism reused, rendering doesn't be**: `collector`-kind modules have no standalone detail page (`hub/open.js`'s `openModuleNode` just toggles the left-panel tree's expand state for them) — since Dragon has no left-panel tree to expand, it needed the same kind of drill-down state Wyvern already solved. `S.dragonBrowsePath` is structurally identical to `S.wyvernBrowsePath` (same array-of-ids breadcrumb, reset at all the same navigation points), but each level renders as a freeform draggable board instead of Wyvern's fixed grid — that's the actual differentiator, not the underlying plumbing.
  - **Deliberate simplification, called out rather than hidden**: card positions persist client-only in `S.settings.dragonLayout[nexusId][parentKey][moduleId] = {x,y}` (same localStorage tier as theme), *not* a new DB table like `designer.js`'s own `designer_node`. Nobody asked for cross-device position sync, so the schema work wasn't done — upgrade path is a straightforward mirror of `designer.js`'s own DB+IPC pattern if that's ever wanted. Modules with no saved position get a deterministic grid slot (`dragonNodePosition`) rather than piling at `(0,0)`. No custom pan/zoom either — the board just scrolls natively; also flagged as a "ceiling," not an oversight. No user-editable edges/connections (unlike `designer.js`'s click-to-connect) — the parent/child hierarchy already exists in the module tree, so a second editable-edge system would have duplicated the Nest tree's own drag-to-reparent feature for no requested benefit.
  - **Guard generalization, not duplication**: `builder.js` already had three `workspaceStyle === 'wyvern'` checks (no tab strip, no split buttons, no drag-to-split) and `hub/menus.js` had one more (hide "open in new pane") — all four widened to `workspaceStyle !== 'drake'` so Dragon inherits the same single-view behavior without a second copy-pasted `'dragon'` branch anywhere.
  - **Live-verified via `run-dracondex`** (dispatched to the `app-run-tester` agent, real Electron, not the web-driver fallback): nav-sidebar stayed visible while left-panel/builder-tabs hid correctly; the board rendered both seeded modules as cards; dragging a card and reloading the whole window confirmed the position survives via `dragonLayout`; right-click showed "open in new window" but correctly omitted "open in new pane"; clicking a collector card drilled in with the breadcrumb updating, and clicking a leaf module opened its normal Inspector detail view with a way back to the board via the nav-sidebar home icon; switching back to Drake afterward confirmed the pane tab strip and "open in new pane" context-menu item both came back exactly as before.
- [x] **Settings page — "Workspace Style" picker** (this session, `src/renderer/core/workspace-style.js`, new). Registered as a fourth page in the Setting window's existing `workspace` group (alongside Theme/Text & Size/Tool Toggle) via the same `registerSettingPage()` seam Part 1's Setting rework introduced — no new top-level group needed. Renders 3 mockup cards (Drake/Wyvern/Dragon) using the same `.prefs-theme-cell`/`.prefs-theme-grid`/`.prefs-theme-name`/`.prefs-theme-check` classes the Theme page already established, with small CSS-drawn wireframe previews (no image assets) rather than real screenshots. Clicking a card only **stages** the choice in `S.settingPendingWorkspace` — it does not apply live, unlike theme/language, because a workspace-style switch changes the whole chrome and needs a fresh boot. An "Apply & Restart" button appears once the staged choice differs from the current one; clicking it confirms via `uiConfirm()` (the same pattern `settingProfileRestore()` already used for its own `location.reload()` in `core/account.js`) before writing `S.settings.workspaceStyle` and reloading. This is what makes all three styles — including the already-shipped-but-previously-unreachable Wyvern — pickable through real UI for the first time; before this, only the `?workspace=` query param worked. Live-verified via `run-dracondex`: 3 cards render with Drake pre-checked and no Apply button showing when nothing's changed; picking Wyvern and Dragon each showed the button, confirmed, reloaded into the right chrome; picking Drake again restored the original UI with no regression.

**Part 2 complete** — Wyvern (previous session) plus Drake/Dragon/the Settings picker (this session) all shipped and live-verified.

**`Plan.md` rollout complete** — both parts of this cycle (Cloud Sync Function + Setting, and New Workspace) shipped. No open follow-ups were identified for Part 1. Part 2 leaves two upgrade paths on the table by design, not oversight: Dragon's card positions could move from client-only localStorage to a real DB table if cross-device sync is ever requested, and its board currently has no custom pan/zoom (native scroll only). Also worth noting for future test-tooling work (not a product bug): `run-dracondex`'s cold-boot "app ready" wait selector times out when the persisted `workspaceStyle` is Wyvern/Dragon, since both hide `#left-panel`, which that selector currently waits on.

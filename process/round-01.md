Dragging the handle's left edge leftward increases width (the panel's right edge is anchored against the window edge, so the delta is subtracted, not added). - [x] 2. Flexible recursive split-layout system, replacing the fixed 1/2/4-layout model above
  - **Confirmed with the user**: "horizontal parallel" = the side-by-side layout that already existed; "vertical parallel" = new, stacked top/bottom. Also confirmed to go beyond a few more named presets — a full VS-Code-style recursive split tree where any pane can be split in either direction on demand, reaching arbitrary arrangements (not just a fixed menu of shapes) — since this also sets up Part 4 topic 3 (auto-split-on-drag-to-edge, still not built) as a natural follow-up.
  - **Key architecture decision**: kept two identity schemes deliberately independent. `S.builder.panes` stays a flat, index-based array — every tab-management function built in Part 3/Part 4 topic 1 (drag-reorder, cross-pane move, pop-out-to-window, close/switch, `paneIdx` baked into dozens of `onclick` template strings) needed **zero changes**. A new, separate `S.builder.layoutTree` describes only the geometry: leaves are `{type:'leaf', paneIndex}` pointing into the flat array, splits are `{type:'split', dir:'h'|'v', ratio, id, a, b}`. Splitting/closing a pane only ever touches this second tree, never the tab-management code.
  - `builderSplitPane`/`builderClosePane` mutate tree nodes **in place** (a leaf becomes a split, or a parent gets overwritten with its surviving sibling's fields) rather than replacing references — so a node's parent never has to be told about a new child object. Closing folds tabs into the sibling's first leaf (same "fold into survivor" convention the old fixed-layout model used) and renumbers every later `paneIndex` after the flat-array splice.
  - **Bug found and fixed during live verification**: `Object.assign` for the in-place node mutation above doesn't clear fields left over from a node's previous `type` (e.g. a promoted leaf keeping its old split's stale `ratio`/`a`/`b`, confirmed via `JSON.stringify` on the live tree mid-test). Harmless in practice — every reader branches on `node.type` first — but a real landmine for future code that doesn't. Fixed with a `mutateNode()` helper that clears all of a node's own keys before reassigning, so a node's shape always matches its current `type` exactly.
  - Rendering (`renderLayoutNode`) recurses the tree, reusing existing `.bpane`/`.bsplit` DOM elements by index/id rather than tearing anything down — relies on `element.appendChild(existingNode)` **moving** an already-attached node rather than destroying it, so a pane surviving a further split or a sibling's closure keeps its live content (mounted editors, listeners) exactly like the old fixed-grid renderer's unfocused-pane guarantee.
  - Resize handles are now per-split-node (`ensureSplitHandle`, one per `.bsplit`) instead of at most one-of-each globally — `startBuilderSplitResize` closes over the specific node reference being dragged, so siblings/other splits are provably unaffected (verified live: resizing an outer split's ratio left an inner nested split's own ratio unchanged).
  - Title-bar `#layout-menu` repurposed from a 3-item `[1,2,4]` list into a one-shot preset gallery (`builderResetToPreset`: `1`/`2h`/`2v`/`3`) — labels stay numeric/symbolic ("1×"/"2×"/"3×", `data-no-i18n`), matching the original menu's own convention exactly, so **no new i18n keys were needed for the menu itself**. Only 2 new keys (`splitPane`/`closePane`) were needed, for the new per-pane split/close button tooltips.
  - **Deliberate behavior change**: split ratios and the tree shape are no longer persisted to `localStorage` across restarts (Part 4 topic 1's `colRatio`/`rowRatio` persistence is removed along with the code that used it) — a ratio has no meaning without the specific tree shape it belonged to, and that shape was never persisted either (tabs/panes are already pure in-session state). Simplification, not a regression.
  - Removed rather than left as dead code: `builderSetLayout`, `builderPaneGridArea`, `applyBuilderGridTemplate`, `ensureBuilderHandles`, `startBuilderColResize`, `startBuilderRowResize`, `BUILDER_COL_RATIO_KEY`, `BUILDER_ROW_RATIO_KEY`, and the `.bl-1`/`.bl-2`/`.bl-4` CSS rules — confirmed via repo-wide grep that nothing else referenced them.
  - Live-verified via a one-off Playwright script: split horizontal then split the new pane vertically (3 panes, correctly nested, not just the 3 named presets — proving arbitrary nesting actually works); resizing one split's handle left a nested split's ratio untouched; closing a *middle* pane correctly folded its tabs and renumbered the remaining panes (not just the last-index case); the "3×" preset produced the exact long-left/two-stacked-right shape from a cold single-pane state; the Module Inspector dock correctly shows only in true single-pane mode and hides under any split, screenshotted at each step.
